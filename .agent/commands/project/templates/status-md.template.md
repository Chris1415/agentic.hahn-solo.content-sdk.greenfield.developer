## Generation rules (for the command that writes this file)

This block is documentation for the writer, not part of the rendered file. Strip it from the actual STATUS.md output.

**Sources to scan, per work item in `project-planning/specs/`** — scan ALL THREE families: `prd-NNN.md`, `frd-NNN.md`, `bug-NNN.md` (schema 8+):
1. Read the spec's frontmatter to resolve the `run_manifest` path; fall back to scanning `workflow/run-*.json` for `canonical_artifacts.prd == <spec>-NNN.md`. Read `work_item_type` from the manifest (missing → `prd`) for the Type column.
2. Read that manifest: `status`, latest `stage_history` entry, `smoke_outcomes`, `operator_attention[]`, `implementation.branch_name`, `implementation.merged_prs[]`, and `notes.program` (for the Programs section below).
3. The title comes from the spec's § 1 (Executive Summary / Summary) first sentence, truncated to ~60 chars. **Under a template swap, resolve § 1 through the active pack's `overrides_section_map` first** — a swapped spec may have no § 1 at all (the marketer brief opens with "What we are making"), and this rule lives here rather than in `/create-prd`, so nothing pointed it at the map. A run had to notice on its own in 2026-08-27; if the map has no entry, fall back to the spec's first heading.

**Programs section.** Scan every manifest for `notes.program`. Group members by `notes.program.id`; each group renders one `###` block. Rules:

- **Omit the whole `## Programs` section** when no manifest carries `notes.program`. Do not emit an empty header — most products are single-spec and the section would be pure noise.
- **`M` is `notes.program.total`, not the number of manifests found.** A program's later members have no manifest until their `/create-prd` runs — render them from `notes.program.members[]` with `Item` = the reserved `PRD-NNN` (or `(unassigned)`) and `Status` = `planned`. Showing only the written members is the exact blindness this section exists to remove.
- **`N` counts members whose manifest `status` is `shipped` or `shipped_with_caveats`.** A member with no manifest is never counted as shipped.
- **Conflicting `total` across members is a defect, not a rendering choice.** When members disagree, render the **highest** `total`, and add a `[warn]` entry to *Open items*: `program <id> members disagree on total (<values>) — re-sync notes.program across every member`.
- The **Delivers** cell comes from that member's `deliverable` line (one sentence, ≤ 100 chars). It states what the item delivers *on its own* — if it can only be described as "groundwork for the next one", the split failed the shippability test and that belongs in Open items as a `[warn]`.

**Cell width — HARD CAP.** The **Stage** cell is **one sentence, ≤ 200 characters**. Name the stage and the single most important outcome; nothing else. The Title cell stays ≤ 60 chars.

Everything else belongs in the **ship report**, which the Manifest column already points at: test counts, per-AC breakdowns, code-review tallies, caveat prose, PR narratives, probe outcomes, milestone commentary. STATUS.md is an **index**, not a digest — a reader scans it to find which run to open, then opens that run's ship report.

Rationale: uncapped Stage cells were observed growing to ~2,000 characters each, taking one product's STATUS.md to 61 KB across 20 rows. The file is regenerated wholesale on every refresh, so every ship rewrote all 61 KB — the churn is expected, but the diff size was not. If a fact seems too important to omit, it is important enough for the ship report.

**Sorting:** Programs in program-id alphabetical order, members by `index` ascending. Work items grouped by type (PRD, then FRD, then bug), each in ascending NNN order — OR a single interleaved table sorted by most-recent activity when the operator prefers a timeline view (default: grouped by type). Open items in `blocker > warn > info` order, then by `raised_at` ascending. Smoke status in item-ascending order. Last activity in `exited_at` descending (most recent first), keep ~5 entries.

**Refresh triggers:**
- `/create-prd` kickoff (step 0a, after the durability-tiering backfill) — refresh before writing the new PRD-NNN+1 (so the new PRD's `in_progress` row is captured).
- `/ship` close (step 15b — after manifest write, before PR creation) — refresh to lock in the shipped status, PR URLs, and smoke outcome.
- `/cleanup-project-planning` removal — file is deleted; next `/create-prd` or `/ship` regenerates.

**No other refresh triggers.** `/architect` / `/task-breakdown` / `/implement` / `/code-review` / `/test` do NOT refresh STATUS.md — they touch the run manifest, and STATUS.md's "current stage" comes from the manifest at next regeneration.
