# ship.pre_commit — Content SDK close-out (CODE ONLY, preview context)

> **Pack stage body.** Injected by `platform:content-sdk` at the `ship.pre_commit` anchor. Core
> `/ship` runs it **before the git commit**, so everything a step captures lands in the same commit.
> Extracted verbatim from `10-ship.md` on 2026-08-22 (tranche 4) — at ~48 lines, the largest single
> platform block in the pipeline. It was already self-contained and already emitted its own
> `stage_history` entry, which is exactly why it lifts cleanly.

Runs **before** the git commit so the captured items land in the same commit. **`/ship` ships CODE ONLY against the PREVIEW context — it does NOT publish** (preview-first / publish-last, `.agent/glossary.md` § "Preview-first delivery"). Publishing everything, the LIVE-context redeploy, the pull of authored *content* items, and the 200-not-302 media gate all move to the final **`/publish`** step, which runs after the content phase.

1. **Pull the live-authored CONTENT-MODEL items into the CM code base (pull-on-ship).** During `/implement` the **structural** items (templates / renderings / datasources) were authored **live** in the CM; capture them now into the CM code base resolved earlier (the `cm/` folder for a NEW CM, or the operator's existing CM code path for an EXISTING CM). **Re-enable + detokenize** the Project serialization module (`authoring/items/example.module.json` — undo the initial-deploy `.disabled`) with the **verified** real collection/site names, then `dotnet sitecore … ser pull`. Items flow CM→repo via pull; never push. Confirm `.sitecore/user.json` stays gitignored. (The **authored content** items — real brand copy — are authored AFTER ship in `/author-content`; **`/publish`** pulls those.)
2. **Editing host deploy — PREVIEW context (the content-phase preview surface). Vercel — LIVE-pinned, NOT a preview surface.** Deploy the head-app code to the **editing host**. Its Edge context is **platform-injected**: set no `SITECORE_EDGE_CONTEXT_ID` / `NEXT_PUBLIC_*` on it (a same-named upsert breaks the rollout, `/provision-sitecoreai` § 5c), and run `assert-eh-vars.mjs --env <ehId>` (exit 0) before the deploy. The editing host is the surface the content phase (`/author-content` ⇄ `/test-content`) previews on (`get_page_preview_url`; glossary § "Preview-first delivery" → Surfaces), so it must serve the shipped components on preview. **Vercel is the LIVE surface reserved for `/publish`, not a preview surface:** if unlinked, link it and set `SITECORE_EDGE_CONTEXT_ID` + `NEXT_PUBLIC_SITECORE_EDGE_CONTEXT_ID` to the **LIVE** context id — **on all three Vercel targets (`production`, `preview`, `development`), same value each** (`/publish` § "Standing up the delivery surface" step 3 has the loop and the reasoning). Setting production alone is the observed defect: every Vercel *Preview* deployment — i.e. the PR this very stage opens — then fails to build on the missing context id, while `vercel --prod` stays green. Back up `.env.local` before `vercel link` — linking clobbers env vars. Do **not** stand up a preview-context Vercel — and **never** put any Vercel target on the PREVIEW context on a URL anyone outside the team can reach (measured 2026-09-28: a clone's public production URL served unpublished content for a day by operator override): all three targets carry the **LIVE** id, because a Vercel Preview deployment is a branch build of the live surface, not a preview surface. The live Vercel deploy/redeploy is **owned by `/publish`** (rule `80` § 7); Vercel legitimately shows empty until then (publish-last, by design).
3. **No publish, no media gate here.** `/ship` does not publish and does not run the 200-not-302 media gate — nothing is published yet (preview-first). Both move to `/publish` (they depend on published content on the LIVE context).

   **Preview has a blind side — name it, don't imply it passed (rule `85-preview-live-divergence`; `.agent/glossary.md` § "Divergence class (preview vs live)").** Everything `/ship` verified, it verified against **preview**. Preview and LIVE Edge do not resolve identically, so a class of claims is **structurally unverifiable at `/ship`** and stays open until `/publish`: **route-path form** (preview resolves both the raw and the slugified form, live resolves only the slugified one — links that work on preview 404 live), **media resolution** (the 200-not-302 gate is a `/publish` step), and **cache / tag semantics** (ISR windows, revalidation, Edge tag invalidation — all behaviours of *published* content). Record them in the ship report under a `## Unverifiable until /publish` heading, one line each naming the claim and what will verify it, and never fold them into a passing test count. Not theoretical: a run went live with **4 of 21 internal links 404-ing**, every one of them green on preview.
4. **Editing-host git link — VERIFIED at ship (`/provision-sitecoreai` § 5b owns the linking).** Since 2026-08-13 the link is made at **provision**, right after the initial upload deploy — so by `/ship` the normal state is already git-linked and this step is a **read-back**, not an action. It stays enforced because an upload-mode EH silently rots: `/ship` merges the PR, everyone assumes the host followed, and the content phase then authors against a host serving the bare scaffold — Pages shows an author a page of missing components while the local build and Vercel both look perfect.

   **Check the mode against the LIVE environment** (`GET /api/environments/v2/{ehEnvId}` → `repositoryDetails` / `repositoryBranch` / `deployOnCommit` — **Use the v2 environment read for this, never v1** — the Deploy API's **v1** environment read carries **no `repositoryDetails` field**, so a read-back against it can never confirm a link, whatever state the environment is in (measured 2026-09-28 on a clone's editing host: the link was real, the v1 read could not show it, the v2 read did). — or `dotnet sitecore cloud environment info -id <ehId>`) — **never from the manifest**, which can be stale. Then:

   | Mode | Action at `/ship` |
   |------|-------------------|
   | **git-linked** | Verify the linked **repo + branch + path** still match this head app **and `deployOnCommit` is `true`**. Both are automation-client-writable (`PUT .../repository` → 204 on an already-linked env), so **fix a wrong branch or a false `deployOnCommit` in place** rather than reporting it. Then continue to step 4a. |
   | **upload-mode** | Provision hit the **first-link 403** and the operator was not available. Attempt the `PUT` once more; on a repeat 403 this needs the integration's creator — a device-flow token or the Deploy Portal (`/provision-sitecoreai` § 5b has the full contract and the measured boundary). If the operator declines, record `editing_host: upload-mode (operator declined link)` as a ship caveat — a known-rot state, not a neutral choice. |

   **Whenever a first link is made here, do NOT mirror `.env.local` onto the editing host first** (`/provision-sitecoreai` § 5c, inverted 2026-09-11) — the platform injects the Edge context into the rendering-host container, and an upsert of the same names is what made every API-created host on one CM fail its rollout. Assert `variable list -id <ehEnvId>` is empty of them before the linked build fires.

   **Traps that have actually bitten (`reference_xmcloud_editing_host_git_linked_repo_rename_breaks_pull`):**
   - **A git-linked EH builds a FIXED branch.** Code must reach **the branch the EH builds** — a feature branch pushed but unmerged rebuilds the old commit.
   - **`deployOnCommit` decides whether the merge itself deploys.** Measured 2026-08-13, all five linked editing hosts then in use already carry `deployOnCommit: true`, so the merge normally fires the build on its own — but it is **per-environment state, so read it, don't assume it**. When it is `false`, step 4a's explicit trigger is the only thing that deploys.
   - **`origin/main` after a PR merge is a merge commit, not a fast-forward of the feature branch.** Verify with `git merge-base --is-ancestor origin/main <branch>`; if it is not an ancestor, do a real `--no-ff` merge and confirm `git diff <branch> HEAD` is empty.
   - **`--upload` is REJECTED on a git-linked env** (*"Uploading source code is not permitted"*). Never force an upload deploy over a git-linked host.
   - **Renaming the GitHub repo breaks the pull** on a private repo — the GitHub App grant loses access and the build fails with `Failed to download content from GitHub`. Repair is a Portal re-authorization or an unlink-then-upload; **neither is CLI-only**.
   - Deploy needs a **Deploy-scoped token** (`xmclouddeploy.deployments:manage` + `rh:mng`). The `.env.local` CM client (`xmcloud.cm:admin`) is **scope-insufficient** — 403 on the Deploy API. Use `dotnet sitecore cloud login` (device flow) or the org deploy-admin client.

4a. **Deploy the editing host with the shipped code, and verify it — the content phase depends on it.** After the PR merges (step 18), the EH must actually be serving this run's components before `/discover-components` or `/author-content` runs. Trigger explicitly rather than assuming:

   ```
   dotnet sitecore cloud editinghost deploy -id <ehEnvId> --no-watch     # git-linked: NO --upload
   ```

   Poll to terminal (`GET /api/deployments/v3/{id}`), then **assert freshness from the deployment RECORD** — not by fetching a page. **A green deployment status alone is not proof the right commit built**, but the served markup cannot be used as the proof either: the editing-host URL **403s** unauthenticated, and `/api/editing/render` **302s into the OIDC login** even with the correct secret, so neither can be driven headlessly. Assert instead, all three:
   - the most recent deployment for the EH environment is **terminal and `Complete`**, with **every phase** complete (not just the rollup);
   - the deployment's **`commitId` equals `git rev-parse origin/main`** (or whatever branch the EH builds). **This is the whole assertion** — it is a direct equality against a first-class field, so it needs no inference:

     ```sh
     # newest deployment for THIS env, then compare
     dotnet sitecore cloud deployment list -id <ehEnvId> --json   # or GET /api/deployments/v1
     git rev-parse origin/main
     ```

     *Verified live on one EH, 2026-08-27: `commitId: "<40 hex>"`, a plain 40-char SHA.*
   - **its start time is LATER than the merge commit's timestamp** — keep this as a corroborating check, and as the **fallback** when `commitId` is absent (a manually-created deployment reads `Deployment created by <user>`). If you fall back, **say so explicitly** rather than implying a SHA was compared.

   > **Do not parse the SHA out of `triggerMessage`.** It also carries one, as an HTML anchor (`<a href="…/commit/<sha>">Commit <sha></a>`), and this contract used to instruct parsing it. That is fragile string-handling over a display field when `commitId` sits on the same record as a clean value — and it silently yields nothing for a manually-triggered deployment.

   🔴 **`GET /api/deployments/v1?environmentId=…` IGNORES the filter.** Measured twice, most recently 2026-08-27: a query scoped to one site returned **10 deployments, only 4 of which belonged to it** — the rest were a sibling brand's. Asserting freshness against another environment's deployment is a green light for a host that never rebuilt. **Filter the response on `d.environmentId === <ehEnvId>` yourself before reading the newest.** This is the same class as the XM Apps `?environmentId=` trap; two independent endpoints on this platform now accept the parameter and disregard it, so treat it as a platform-wide assumption to distrust.

   List them with `dotnet sitecore cloud deployment list -id <ehEnvId> --json` from the `cm/` folder (the CLI is a local tool there), sort by `startedAt` descending, and read the newest. Phase fields are `provisioningStatus` / `buildStatus` / `deploymentStatus` / `postActionStatus` plus the `calculatedStatus` rollup; **`2` = Complete** on each. *Verified live on a prior run, 2026-07-30: PR merged 12:28:42Z, a deployment auto-started 12:28:44Z with `triggerMessage` naming the merge SHA — the git link fires in ~2s.*

   Record the result in the ship report under `editing_host_freshness`, and write `provisioning.editing_host.deployed_sha` to the run manifest (or `null` + the timestamp evidence when the SHA is unavailable).

   **An EMPTY editing-host list is not evidence of absence.** `GET /api/editing-hosts/v1?environmentId=…` (the Deploy API's `host.list-env`) returns `[]` for a healthy, git-linked, successfully-deployed editing host — measured on one EH environment, 2026-08-11, minutes after a green deployment of a known commit. Do not read `[]` as "no host is linked" and do not re-link on the strength of it. **Read the host URL from the CM instead**, where it is authoritative: the Rendering Host items under `/sitecore/system/Settings/Services/Rendering Hosts/<name>` carry `ServerSideRenderingEngineApplicationUrl` / `…ConfigUrl` / `…EndpointUrl`, and the site's `RenderingHost` setting names which one it uses. Guessing the URL from `platformTenantName` does not work — that host does not resolve; the EH hostname is an unrelated `xmc-<id>-eh.sitecorecloud.io`.

   **Git-linked EHs deploy on merge, not on `/ship`.** When the EH is git-linked with `deployOnCommit`, the merge itself triggers the build — so this assertion runs *after* the PR merges, and a `/ship` that stops at "PR opened" has not satisfied it. Do not mark the gate passed on an unmerged PR.

   **If the EH is stale or the assertion fails, the content phase MUST NOT start** — see `/discover-components` and `/author-content`'s entry gate. Surface it as a `[BLOCKER]`.
5. **Accept the generated `.sitecore` maps as build output.** The component/site maps (`.sitecore/component-map.ts`, `component-map.client.ts`, `import-map.server.ts`, `sites.json`) are regenerated by the build (and by `/implement` § "Generated `.sitecore` maps"). Commit whatever is present — **do NOT revert them as drift** (they legitimately change when components are added/removed); they are deterministic artifacts the app imports, owned by the commit.

6. **ASSERT the delivery surface exists — a live run must have somewhere to go live (ENFORCED).** Step 2 says to link Vercel if unlinked. Saying it is not a gate: **an instruction with no assertion behind it is exactly rule `88`'s shape**, and this one failed silently on a prior run (2026-08-27) — provisioning stood up an editing host, nothing ever created a Vercel project, `/ship` closed green, the whole content phase ran, and the absence surfaced only at `/publish` step 6a when the link-crawl had **no URL to crawl**. Every sibling brand had one; this run's gap was invisible for the entire build.

   **The editing host is NOT a fallback.** It `403`s anonymously with `x-robots-tag: noindex,nofollow` — it is the authoring surface by design, so "we can just use the EH URL" is not an option, and a crawl driven authenticated or with `curl -L` to work around the 403 is precisely the false-pass shape `/publish` § 6a forbids.

   So assert one of two states and **record which** in `provisioning.delivery_surface`:
   - **`{ kind: "vercel", project: "<name>", live_context_verified: true, env_targets_verified: ["production","preview","development"] }`** — the project exists and the **LIVE** context id is present in **both** `SITECORE_EDGE_CONTEXT_ID` and `NEXT_PUBLIC_SITECORE_EDGE_CONTEXT_ID` **on all three targets**. Verify by reading it back; do not infer it from having run the set command.

     **Read the VALUE per target, not the presence list.** `vercel env ls` prints one row per (name, target) pair with the value shown as `Encrypted`, so it can tell you a key exists on Preview but never that it holds the right id — and a Preview target seeded with the *preview* context id passes a presence check while serving unpublished content at a live-looking URL. Pull each target to a scratch file and compare:

     ```sh
     for target in production preview development; do
       vercel env pull --environment="$target" "$TMP/.env.$target" --yes
     done
     ```
     ⚠️ **Never let `vercel env pull` default its output path** — it writes `.env.local` and will clobber the app's local development env. Always pass an explicit scratch path.

     **A missing target is a finding, not a nit:** any of the five absent from `preview` means the PR opened by this stage cannot build. Fix it here (the loop in `/publish` § step 3) rather than recording it — this is a two-command repair, not an operator decision.

     **When `variables.freshness` is `osr`** (ratified by the publish-freshness ADR), the same loop also sets **`SITECORE_REVALIDATE_SECRET`** on all three targets (a generated value, never empty) and the same read-back proves it non-empty on each, recorded as `revalidate_secret_targets_verified: [...]`. An unset or blank secret makes `/api/revalidate` an **open endpoint** (live on 2.4.0 and 2.5.0: no header, `200`), so a target without it is a `[BLOCKER]`, not a nit. If Vercel Deployment Protection covers the URL the webhook will call, also generate the project's Protection Bypass for Automation secret (kept in the secret store for `/publish`). Skill: `content-sdk-app-router-cache-components-and-osr` § Hard rules.
   - **Under `variables.delivery_visibility: private`** (the `method:clone` default; `/publish` § "Delivery visibility" has the contract) the Vercel state additionally carries **`visibility: "private", gate_verified: true`** — the access gate is deployed and anonymous `/` and `/robots.txt` both answer **401** with `X-Robots-Tag: noindex`. Verify by an unfollowed anonymous request, never `curl -L`. A private-by-contract surface that answers 200 anonymously is a **`[BLOCKER]`**: the first production deploy must not be the moment a copy of someone else's site goes public.
   - **`{ kind: "none", reason: "<operator's words>", decided_at: "<iso>" }`** — a deliberate, operator-stated decision that this product ships without a public surface (a tenant-only demo, an internal-authoring-only build). Legitimate, but it must be **said**, not defaulted into.

   Neither present → **`[BLOCKER]`**, surfaced at the `/ship` close: *"No delivery surface. This run can be published to the tenant but cannot go live, and the live gates cannot run."* Do not close green on the assumption that `/publish` will sort it out — `/publish` is where the cost is highest and the operator is already waiting on a URL.

Record a `stage_history` entry `{ stage: "content_sdk_closeout", agent: "13-devops-engineer", outcome: "completed", one_line: "ser pull N content-model items into cm/; editing host deployed on PREVIEW; delivery surface <vercel:<project>|none:<reason>> asserted; publish deferred to /publish" }`.
