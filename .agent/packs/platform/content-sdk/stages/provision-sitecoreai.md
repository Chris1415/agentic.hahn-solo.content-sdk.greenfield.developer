# /provision-sitecoreai — Stand up the decoupled cloud topology + deploy the baseline (BEFORE /implement)

## Pipeline position

Runs **between `/task-breakdown` and `/implement`**, for runs on this platform (this stage ships only with this pack, so the condition is the pack itself). It is "step zero of implementation" — DevOps preparation that has nothing to do with the architecture; it stands up the tenant so `/implement` drops into a prepared, running head app.

- **NEW site** → provision the full cascade (project → CM env → editing host → collection → site), deploy, initial pull.
- **EXISTING site, all rungs present** → provision is a near no-op: scaffold/deploy the head app (editing host) only; the CM + site already exist (discovery already pulled the content model).
- **`frd` / `bug` / non-Sitecore** → not applicable.

## Why this exists (the load-bearing reason)

SitecoreAI is GitOps/deploy-based: an environment is useless until a **deployment** provisions it, and a Content SDK head app must be deployed as a **decoupled editing host** against a CM. The generic pipeline has no stage that talks to the Deploy API. This command is that stage — it executes the **provision plan** from `/discover-sitecoreai` and leaves a deployed CM + editing host ready for live authoring during `/implement`. (The CMS-side build the operator used to do by hand.)

## Mechanics — DevOps Engineer (13)

Spawn agent 13 via `Agent(subagent_type: "devops-engineer")` (applies its pinned `model`/`effort` — rule 72; include `Output Level: <minimal|verbose>` per rule 73). The steps below are the contract + the gotchas that MUST hold. Auth + all cloud ops run **non-interactively from one org "deploy admin" automation client** (operator-provided id+secret; created once in the Deploy Portal). `dotnet sitecore cloud login --client-credentials` for CLI ops.

**Domain skills to load (before scaffold/deploy/chrome GraphQL):**
- `content-sdk-website-build-flow` — CM-then-wait-for-Edge before editing-host deploy; Page/Partial Design chrome skeleton GraphQL; RenderingHost binding recipe
- `setup-content-sdk` — head-app App Router scaffold
- `sitecoreai-cli-cloud-workflow` — CLI login / environment connect / ser pull
- `sitecoreai-serialization` — module design for step 7c: one module per collection in its own folder, include scope, push policy, full record vs shell

## Steps

1. **Resolve workspace + plan.** Read `product-workspace.md` and the run manifest. Load the provision plan from `/discover-sitecoreai` (which rungs exist). Confirm this pack is active in the run manifest's `packs` block; if not, stop and report the misroute — a stage body that only ships with its pack should never be executing otherwise. Collect the org deploy-admin client id+secret (session-only).

2. **Auth + inventory the live org.** `POST auth.sitecorecloud.io/oauth/token` (client_credentials, audience `api.sitecorecloud.io`). `GET /api/projects/v1` to see what already exists. **Read before you create** — never trust the plan's "absent" without confirming against the org.

3. **Provision the cascade (idempotent, first-missing rung down):**
   - **Project** (if absent) — `cloud project create -n "<deploy_project_name>"` (Deploy API `POST /api/projects/v1`). The Deploy project name is the **verbatim** `deploy_project_name` from the manifest (may contain spaces/caps — quote it); the **space-free `project_slug`** is only the local folder name (§ 1b-i). One Deploy project = one project folder = the CM that all its head apps bind to.
   - **CM-only env** (if absent) — `cloud environment create --project-id <id> -n cm --cm-only --prod`. The **`--cm-only`** flag is what makes it decoupled (omit → coupled "Legacy"). `tenantType` 0=NonProduction, 1=Production. Handle quota `402` as a hard gate (free a slot / upgrade). **The quota is PER PROJECT and PER tenantType** — measured 2026-09-10 on one org: *"the organization tier does not allow more than 10 non production environments"*, with all 11 projects sitting at exactly 10. A **prod** slot may still be free when nonprod is full, so read the 402's own wording before reporting the project as full. And a 201 is not proof: verify the created environment carries `type: "eh"` and its `editingHostEnvironmentDetails.cmEnvironmentId` — a request that omits the binding is accepted and silently creates the WRONG KIND of environment, consuming a slot.
   - **Editing host** (if absent) — `cloud editinghost create -n <site> --cm-environment-id <cmEnvId>`. `editinghost create` takes **no repo arguments** — create-then-link is always two steps.
   - **The git link happens in step 5b — AFTER the initial upload deploy, never before it.** `--upload` is rejected the moment an environment is linked ("upload initially, git thereafter", step 5), so linking here would break the very deploy that proves the topology.

4. **Scaffold the deployables** (per the architect's stack). A CM env is 1:1 with a CM code base — resolve it, don't always create it.

   **First read this run's `repo_topology` from the manifest** (`/create-prd` asked it at intake; default `repo-per-deployable`). It decides **where the head app sits, where the git root is, and how many build descriptors exist** — and the two answers are not interchangeable:

   | | `repo-per-deployable` *(default)* | `monorepo` |
   |---|---|---|
   | Head app | `<project_root>/<head-app-slug>/` — sibling of `cm/` | `<cm_code_base>/sites/<head-app-slug>/` |
   | Git repos | `cm/` + one per head app | one, at `cm/` (or the operator's existing CM repo) |
   | Descriptors | CM: `renderingHosts: {}` · head app: its own, `path: "./"` | **ONE**, at the repo root: `authoringPath` + `renderingHosts[].path: "./sites/<name>"` |
   | EH deploy `--working-dir` | the head-app folder | the **repo root** (`<cm_code_base>`) |

   **Do not derive this from what you find on disk** — a run that scaffolds into the wrong place still builds locally and fails only at the deploy, by which point the repo has the wrong shape committed. Read the recorded value; where it is absent on an existing workspace, detect it (`sites/<head-app>/` beside `authoring/` under one git root ⇒ `monorepo`) and record what you found.
   - **`cm/` (created by `/discover-sitecoreai`) — REUSE it, do not re-create.** `/discover-sitecoreai` already created the new-CM `cm/` baseline (baseline copy + token-replaced names + the **CM-only `xmcloud.build.json`** from `templates/xmcloud-build/cm-only.xmcloud.build.json` — copied, not retyped; blueprint: `templates/xmcloud-build/README.md` + **disabled Project serialization module** `authoring/items/example.module.json` → `.disabled` + `nuget.config` with the Sitecore feed). **Verify `<project_root>/cm/` (`products/head-application/<project-slug>/cm/`, the PROJECT level) exists**; if it is missing (discover skipped, or a pre-reconciliation run), **fall back** to creating it here from the reference baseline — `cp -r .agent/packs/platform/content-sdk/templates/authoring-baseline/. <project_root>/cm/` (the trailing `/.` is load-bearing — a glob skips `.config/` and `.sitecore/`) — with that same configuration. **EXISTING CM → no `cm/`:** the CM code base is the operator's existing path, reused in place (its serialization module was added during `/discover-sitecoreai`).
   - **The head app** (the workspace `PR` — at the path the table above gives for this run's topology) — **the head app is ALREADY SCAFFOLDED** by `/create-prd` § 10a-4b (first-time repo setup), which seeds a deployable baseline on `main` so a git-linked editing host can build. **Do NOT re-run the generator.** Verify instead: `src/app/` present, `src/pages/` absent, **the descriptor present at this topology's target** — and correct its **`renderingHosts.<key>` to the editing-host name actually created in step 5** (4b resolves it from the naming convention; step 5 is where the name becomes fact). Only when the head app is genuinely absent — a pre-4b run, or a non-content-sdk product — does the scaffold run here, per the rest of this bullet: scaffold the head app **App Router** (`setup-content-sdk`; `--template nextjs-app-router`; verify `src/app/`, HARD STOP if not) into the topology's head-app path. **The head-app folder already holds `project-planning/`** (from `/create-prd`), so the app must coexist with it — scaffold directly into that folder; if the scaffold tool refuses a non-empty target, scaffold into a temp dir and move the app files in **beside** `project-planning/` (never delete or overwrite planning). Then settle the descriptor **by topology**:

     - **`repo-per-deployable`** — add an **editing-host `xmcloud.build.json` at the head-app ROOT** by **copying the template**: `cp .agent/packs/platform/content-sdk/templates/xmcloud-build/editing-host.xmcloud.build.json <head-app-root>/xmcloud.build.json`, replacing `<EDITING_HOST_NAME>`. The CM's own file keeps `renderingHosts: {}`.
     - **`monorepo`** — **add NOTHING at the head app.** The repo-root descriptor (from the authoring baseline, settled at `/discover-sitecoreai`) already carries this host; here you only **verify** `renderingHosts.<key>.path == "./sites/<head-app-slug>"` and correct the key to the real editing-host name. A stray `xmcloud.build.json` inside `sites/<head-app-slug>/` is a **defect** — two files declaring the same `renderingHosts` key is what the blueprint's § 3 invariant 3 forbids — so delete it if a prior run left one. On an **EXISTING CM**, add this host's entry to the operator's file **in place**; never overwrite their file with a template.

     **Do not hand-write either shape and do not restate its values here**: the blueprint (`templates/xmcloud-build/README.md`) is the single source of truth for the shape, the pinned `nodeVersion` and the bump procedure, and a stray literal in prose fails `__tests__/xmcloud-build-blueprint.test.mjs`. (Two disagreeing copies is not hypothetical — it is what this step used to ship.) **The `renderingHosts.<key>` name MUST equal the editing-host name** used in `editinghost create -n <name>` / `editinghost deploy` (or vice versa) — a mismatch and the deploy can't bind the rendering host, in either topology.

5. **Deploy the CM first, then WAIT ~1-2 min for the Edge resource, then the editing host** — do **not** deploy CM and editing host back-to-back with no wait; an empty tenant does **not** remove the Edge-resource timing requirement:
   - **CM** — `cloud deployment create --environment-id <cmEnvId> --upload --working-dir <project_root>/cm/ --no-watch`. **The deployment triggers provisioning, which creates the Edge resource for the env's contextId EARLY in the run.** `--no-watch` returns immediately — but the **upload leg still runs to completion in the foreground**, and killing it (a command timeout, Ctrl-C) cancels the deployment server-side: it lands `deploymentStatus: 3` with `deploymentLastFailureMessage: "Deployment cancelled"` and provisioning/build/postActions all still `NotStarted`. A CM deploy is **~9-12 min**; run it with a matching timeout or in the background, and read that status triple before blaming the code.
   - **`--upload` works ONLY while the environment is not git-linked** (rule of thumb: **upload initially, git thereafter**). Once the CM — or the editing host — is linked to a branch, upload is rejected (`Uploading source code is not permitted. The environment is already linked to a branch.`) and **the linked branch becomes the only deploy source**: land the change on it (push to `main`, or merge a PR from your branch), then fire `cloud deployment create --environment-id <cmEnvId> --no-watch` **without** `--upload`. `deployOnCommit: false` means a push alone deploys nothing. The mode can change between deploys without your involvement — **read the live `repositoryBranch` first, never assume**. (A per-environment link with a `null` project-level `repository` is normal, not a fault.)
   - **WAIT for the Edge resource** after the CM deploy starts, BEFORE deploying the editing host. **The "~1-2 min" figure is wrong for a brand-new environment** — measured 2026-08-13 on a fresh CM env, the preview contextId still returned `The sitecoreContextId does not contain a edge resource` **~20 min after a fully green deploy**, and only resolved somewhere inside the next ~1.5 h. Do not treat a populated `previewContextId` on the env record as proof: the id is minted at **environment creation**, the Edge resource behind it is provisioned separately and later, so the two are independent. **Poll the resource itself** — `POST https://edge-platform.sitecorecloud.io/v1/content/api/graphql/v1?sitecoreContextId=<previewContextId>` with `{ site { siteInfoCollection { name } } }` until HTTP 200. Pass the context id as a **query param**; the `sitecore-contextid` **header** form 404s for every environment including known-good ones, so it is not a signal. The EH's `next build` SSG-prerenders the catch-all route against Edge **at build time**; if the Edge resource for the contextId does not exist yet, the EH build FAILS with `GraphQL 404 "The sitecoreContextId does not contain a edge resource"`. Empty *content* is fine — but the Edge *resource* must exist first, so firing the EH **concurrently with the CM deploy is too fast**. Current scaffold (Next 16.2.x + current Content SDK) still does build-time Edge prerender — always CM deploy → wait for Edge resource → EH deploy.
   - **Pin `@swc/core` before the FIRST editing-host deploy of a new app** — `npm pkg set "overrides.@swc/core=1.16.2"` + `npm install` + a green local `next build`, committed. next-intl pulls a newer `@swc/core` (1.16.13 and 1.16.18 measured) whose native binding cannot load in the platform container (`ERR_SWC_NATIVE_CACHE … parent writable by another user`): at BUILD time on some runs, at `next start` on others (it loads `next.config.ts` through next-intl's plugin) — the build is then green and the rollout fails ~7 min later with "Rendering host … failed to start up" (measured 2026-10-06 and 2026-10-13; the second run read the error from `RenderingHost.<name>.log`). The pin rolled out Complete.
   - **Editing host — after the wait** (no published content required, only the Edge resource): `cloud editinghost deploy --environment-id <ehId> --upload --working-dir <THE DEPLOYABLE ROOT> --no-watch`. **The deployable root is the folder holding the `xmcloud.build.json` that declares this host** — `<project_root>/<head-app-slug>/` under `repo-per-deployable`, and the **repo root `<cm_code_base>/`** under `monorepo` (§ 4's table). Pointing it at `sites/<head-app-slug>/` in a monorepo uploads a tree with no descriptor and the deploy fails `The file xmcloud.build.json is not found` — the same deadlock `repo_setup.deployable_baseline` describes, arriving here instead of at the first git build. The CLI upload is `.gitignore`-aware (excludes `node_modules`/`.next`; do NOT pre-stash). The EH *environment* provisions instantly off the CM env (status 2 in ~3s) and its rendering host is registered into the CM host list at create time; this step deploys the EH *application build*.
   - **The CM↔EH URL link:** the EH gets its own `xmc-…-eh.sitecorecloud.io` URL registered into the CM env's host list (verify: `GET /api/hosts/v1/environment/{cmEnvId}` → `renderingEngineApplicationUrl`/`…/api/editing/render`). (The EH env's own `host` field is a misleading placeholder showing the CM host; the real EH URL is only in the hosts registration.)
   - **Then poll both** to terminal via `GET /api/deployments/v3/{id}` (provisioning ∥ build → deployment → postActions; 0=NotStarted,1=InProgress,2=Complete). On failure, `deployment log -id <id>` and triage ours-vs-theirs.

5b. **Git-link the editing host + set `deployOnCommit: true` — HERE, not at `/ship`.** The initial upload deploy (step 5) has proven the topology; from this point the environment goes git ("upload initially, git thereafter"). Linking at provision instead of at ship means the whole run deploys from the repo, so the host cannot silently rot mid-run while the local build and Vercel both look perfect.

   **Do NOT mirror `.env.local` onto the editing host before linking** — see 5c. The platform injects the editing host's Edge context itself, and an upsert of the same names is what broke every API-created host on this estate (measured 2026-09-11).

   ```
   PUT /api/environments/v1/{ehEnvId}/repository
   { "repository": "<repo>", "repositoryId": "<numeric GitHub id as a STRING>",
     "integrationId": "<sourceControlIntegrationId>", "repositoryRelativePath": "./",
     "repositoryBranch": "main", "deployOnCommit": true }        → 204
   ```

   **Under `monorepo`, every environment links to the SAME repo** — the CM env and each editing host all take that one `repository` / `repositoryId` with `repositoryRelativePath: "./"` (the descriptor sits at the repo root and covers all of them). Two consequences to state in the report rather than discover later: a single push to `main` triggers **one deploy per linked environment**, and unlinking one environment does not unlink the others. Under `repo-per-deployable` each environment links to its own repo and a push moves exactly one.

   `repositoryId` is the **numeric** GitHub id — resolve it locally (`gh api repos/<owner>/<repo> --jq .id`), never through the Deploy API. Reuse `integrationId` from any already-linked sibling environment (the **v2** environment read → `repositoryDetails.sourceControlIntegrationId`; v1 carries no `repositoryDetails`); it is **not** discoverable from `GET /api/sourcecontrol/v1/integrations`, which lists only same-org integrations.

   **What an automation client can and cannot do** — measured 2026-08-13:

   | Operation | Org deploy-admin client |
   |---|---|
   | **First link** (env has no `repositoryDetails` yet) | **403** — creator-only |
   | **Modify an existing link** (branch, `deployOnCommit`, re-link) | **204** |
   | `DELETE .../repository` (also on an already-unlinked env) | **204** |
   | Repository / branch **discovery** through a cross-org integration | **403** — creator-only |

   The 403 is **per-INTEGRATION, not per-scope.** The same token succeeds against a same-org integration and fails against a cross-org one. Do **not** re-diagnose it as a missing scope — the client already holds `xmclouddeploy.sourcecontrol:manage`. Verbatim: *"The source control connection associated with this project was created in another organization. Only the creator '<email>' can perform this action"*.

   **So: attempt the PUT.** On **204**, record `provisioning.editing_host.mode: "git-linked"` — then **PROVE the link deploys before trusting it.** A 204 says the link was accepted, not that a push builds:

   1. **Read the link back** — `GET /api/environments/v2/{ehEnvId}` → `repositoryDetails` non-null, `repositoryBranch` == the branch you set, **`deployOnCommit: true`**. All three, from the environment; never from the request you just sent. **Use the v2 environment read for this, never v1** — the Deploy API's **v1** environment read carries **no `repositoryDetails` field**, so a read-back against it can never confirm a link, whatever state the environment is in (measured 2026-09-28 on a clone's editing host: the link was real, the v1 read could not show it, the v2 read did).
   2. **Confirm a commit produces a deployment carrying it** — after the next push to that branch, the newest deployment for this environment must have `commitId == git rev-parse origin/<branch>` (same assertion as `/ship` § 4a; the link fires in ~2s, measured on a prior run). ⚠️ **Filter the deployments list on `d.environmentId` yourself** — `GET /api/deployments/v1?environmentId=…` accepts the parameter and ignores it.
   3. **If the link is accepted but no deployment ever appears**, treat it as `mode: "upload"` for this run and say so in `operator_attention[]`. A link that does not deploy is worse than no link: `--upload` is **rejected outright on a linked environment** (*"Uploading source code is not permitted"*), so the host has neither deploy path and silently serves whatever it last built.

   Only after 1–3 pass is `git-linked` a claim the rest of the run may rely on. On **403** this is the environment's *first* link and it needs the integration's creator — a **device-flow token** (`dotnet sitecore cloud login` from `cm/`, then `endpoints.xmCloud.accessToken` as the bearer; **back the `cm/.sitecore/user.json` up first**, the login overwrites the client-credentials token) or the Deploy Portal. Relay the device code to the operator, mirror it into `operator_attention[]`, and **fall back to upload mode for this run rather than blocking** — provision closes SOFT. The link is **per-environment and permanent**: this is once per editing host, never once per run.

   **Never gate on `POST /api/sourcecontrol/v1/repository/validate`** — it returns `isValid: true` for repositories the integration cannot even see. Gate on a **non-empty** `GET /api/sourcecontrol/v1/{repo}/branches?integrationId=<id>` instead, where the integration permits the read at all.

   ⚠️ **`DELETE .../repository` is a ONE-WAY DOOR back to manual — do not reach for it as a quick fix.** Once linked, `--upload` is rejected, so unlinking looks like the obvious escape when a git build fails. It is not: after the DELETE the environment has no `repositoryDetails`, so **re-linking is a FIRST link again → 403 → another operator round-trip**. Exhaust the real causes first — app env vars wrongly set ON the host (§ 5c — their presence, not their absence, is the defect), the wrong `repositoryBranch`, or a lost GitHub grant after a repo rename (`reference_xmcloud_editing_host_git_linked_repo_rename_breaks_pull`) — all three of which are fixable **in place** with a 204 `PUT` or a `variable upsert`. Unlink only when the operator is present to re-link.

   **Verification status (be honest in the report).** Measured 2026-08-13: the 204-on-relink, the 403-on-first-link, and the clean no-op left by that 403. **Not** measured: a first link succeeding, and the build that follows it. Treat the first git-linked build on any new environment as an integration boundary — watch it to terminal and assert freshness (`/ship` § 4a) rather than assuming the link implies a good build.

   **CONSIDERED AND DECLINED 2026-08-13 — do not re-propose without new evidence.** A GitHub integration created **inside the org that owns the automation client** would probably lift the first-link 403 and make provisioning fully unattended. It was rejected on **blast radius, not on doubt about the mechanism**: the existing cross-org connector is the single link behind **every** live editing host, and creating a new integration needs a browser round-trip (`POST /api/sourcecontrol/v1/integration` wants `{provider, code, installationId, state}`, the GitHub App OAuth callback triple) that **may** require re-granting the GitHub App installation. If it does, the operation that was meant to save ten seconds per head app instead re-authorizes the connector every existing host depends on. The upside is one operator click per *new* editing host — far too small to justify risking the existing links. **The 403 fallback below is the accepted steady state, not a stopgap.**

5c. **Do NOT set the app's `.env.local` variables on the editing host — the platform injects them, and a same-named upsert breaks the rollout (FORBIDDEN, measured 2026-09-11).** This step used to say the opposite ("mirror the `NEXT_PUBLIC_*` vars onto the platform before the first git build"), and that instruction is the root cause of every API-created editing host that failed on one CM — **five of five** across three runs (two on 2026-08-25, one on 2026-09-11), each attributed to a Deploy-side fault for seventeen days.

   **What actually happens.** `variable upsert` of `SITECORE_EDGE_CONTEXT_ID` / `NEXT_PUBLIC_SITECORE_EDGE_CONTEXT_ID` / `NEXT_PUBLIC_DEFAULT_SITE_NAME` / `NEXT_PUBLIC_DEFAULT_LANGUAGE` with `--target <renderingHostName>` is **accepted** (200), the build is green, and then the rollout never produces a running container: **no `RenderingHost.<name>.log` is ever written** (`environment log list` → `[]`), the deployment sits at "Winter is coming…" and is marked failed at ~+23 min and again at ~+58 min with `postActionStatus 0` and no application error. The one-variable-delta proof: one environment, one artifact, upload mode, same automation client — with the four variables set, a deployment failed after 58 min; with the four variables **removed and nothing else changed**, the next deployment rolled out **Complete in 2.3 min**, wrote the rendering-host log (`Next.js 16.3.4 ✓ Ready`), registered the host on the CM and set `lastSuccessfulDeploymentId`. Cross-checked against every editing host on the CM: the only environments carrying these variables were the failed ones; every working host — Portal-created **and** API-created (one created by API + upload, 2026-09-10) — carries **zero**.

   **Why the old rationale was wrong.** The earlier evidence ("git-linked, zero platform env vars, still serving a stale upload build") was a link that never deployed (§ 5b item 3), not a missing variable — the editing host does not need `.env.local`'s values, because the Deploy platform supplies the Edge context and the editing secret to the rendering host container from the CM environment it is bound to. That is exactly why zero-variable hosts serve Pages correctly. `.env.local` exists for **local dev**; Vercel needs the five values because Vercel injects nothing (`/publish` § Standing up the delivery surface) — the editing host is the one surface that must NOT get them.

   **Rule:** never run `variable upsert` for those four names (nor `SITECORE_EDITING_SECRET`, which the platform rejects on eh environments anyway) against an editing-host environment. **Assert before every editing-host deploy — mechanically, not by reading the list:** `node .agent/scripts/assert-eh-vars.mjs --env <ehEnvId> --org <org> --env-file <cm>/.env` exits **0**; it lists the environment's variables through the Deploy API and exits 1 on any of the five names (case- and target-insensitive). On exit 1, **delete them and record who set them** rather than deploying into a known 58-minute failure. Prose said "assert the list is empty" for one afternoon; a gate that is a sentence is the shape that prescribed the defect in the first place (rule `88`). A variable the run genuinely needs on the host (none is known today) is a probe first — one name, one deploy, the rollout watched to terminal — never the set. Which of the four is individually fatal is **not bisected** (the set is proven, the members are not); a bisect costs one deploy per name and is a legitimate follow-up probe.

6. **Mint the environment automation client** — `POST /api/clients/v1/cm` (org JWT) body `{name, description, projectId, environmentId}` → returns `clientId`+`clientSecret` (no Portal step; secret returned ONCE — capture it). **REQUIRED for step 7** (the org deploy-admin token does NOT authorize XM Apps writes — see below). **Gotcha:** the `description` rejects `(`, `)`, `+` as "unsafe value" (400) — use plain alphanumeric + spaces (hyphens OK). Store the `clientId`/`secret` session-only for `/implement` live authoring + serialization; record only the `clientId` in the manifest (secret redacted).
   🔴 **Store it under an ORG-SUFFIXED key — `SITECORE_CM_CLIENT_ID_<ORG>` / `SITECORE_CM_CLIENT_SECRET_<ORG>` (e.g. `…_ACME`) — never the bare `SITECORE_CM_CLIENT_ID`.** An `.env` can accumulate several estates' clients side by side, and an unsuffixed pair names no estate: it wins every naive lookup chain while telling a reader nothing about which CM they are about to write to. That happened: a publish resolved the wrong estate and returned **HTTP 200**, because the two estates share item GUIDs (one was serialized from the other) and identical client scopes, so auth, scope and id resolution all pass. Verify with `node .agent/scripts/assert-tenant.mjs --org <org> --env <path>`, which mints, reads the token's own `tenant_name` claim and **derives the CM host from it** so the pair cannot diverge. Record the resolved tenant as `provisioning.cm_tenant` in the manifest — downstream live-write stages assert against it.

6b. **Edge administration client — ONLY when `variables.freshness` is `osr` (ratified by the publish-freshness ADR; `go_live`-class).** The OnUpdate Experience Edge webhook that `/publish` registers is managed through the **Edge Admin API**, which an automation client cannot call (org or environment client → `401 edge.cdn.11 … Failed to find tenant`). Create one per environment with the org deploy-admin token: `POST https://xmclouddeploy-api.sitecorecloud.io/api/clients/v1/edge` body `{name, description, projectId, environmentId}` → `201 {clientId, clientSecret}` (secret returned ONCE: secret store only, never chat or manifest). **Read before you create** — `GET /api/clients/v1/environment` lists existing ones (`clientType: 2`); reuse one for this environment rather than minting a second. Verify by minting its token (`audience=https://api.sitecorecloud.io`), reading the `tenant_name` claim (it must be this run's CM tenant — one global host, the token picks the environment) and a `GET https://edge.sitecorecloud.io/api/admin/v1/webhooks` → 200. Record `provisioning.edge_admin_client = { clientId, list_id }` (the list's internal `id` is what `DELETE /api/clients/v1/{id}` takes; deleting by `clientId` 404s). The credential carries `edge.content:clearall` (the environment wipe): handle it like the deploy-admin secret. Whether a deleted client's tokens are revoked is unverified. Skill: `sitecoreai-edge-admin-webhooks` § 1. A non-OSR app (redeploy-on-publish) skips this step.

7. **Collection + site** (if absent) — XM Apps API (`https://xmapps-api.sitecorecloud.io`). **Authenticate with the MINTED CM-environment-client token from step 6, NOT the org deploy-admin token** — the org token (despite `xmcloud.cm:admin`) **401s** on these writes, and its GET returns empty (no visibility).
   - **Collection:** `POST /api/v1/collections?environmentId=<cmEnvId>` body `{name, displayName, description}` — **`description` is REQUIRED** (omit → 400 "The description field is required"). Async → `{handle}`.
   - **Site:** `POST /api/v1/sites?environmentId=<cmEnvId>` body `{siteName, language:"<variables.languages.default>", collectionId, templateId, description}` (default `en`) — needs **`templateId`, NOT `builtInTemplate`** (omit → 400 "templateId field is required"). **Discover templates** via `GET /api/v1/sites/templates?environmentId=<cmEnvId>` → the **"Empty"** headless template = `{2867D289-8951-458A-AF19-CE93A67BB494}` (Home + SXA components, no header/footer); "Basic" = `{5AAE1EEA-EA24-40BF-96F1-1F43DA82C77B}`. Async → handle is `"GUID;podname"`.
   - **Analytics identifier** (site analytics, events and personalization all depend on it): every new site gets one per site language, named after the site (lowercased) in that language: Channels → site → Settings → Site hosts → Analytics and personalization → *Create new* (an operator step: the Sites API host PATCH `analyticsIdentifiers:[{name,language}]` only ASSIGNS an existing identifier, and for an unknown name it still returns 204 and leaves the site flagged "missing its analytics identifier", probed 2026-10-15); read back the Site Grouping `POS` field = `<lang>=<sitename>` (a serialization-pushed site has none, measured 2026-10-15), but that field and `GET /sites/analytics-identifiers/{name}` also pass for a dangling name, so the proof is the portal's Site hosts page showing no "missing analytics identifier" warning.
   - **Job-poll quirk:** the `;podname` suffix makes `GET /api/v1/jobs/{handle}/status` return **404 after the job finishes** — do NOT read that 404 as failure; confirm success via `GET /api/v1/sites?environmentId=<cmEnvId>`.

7b. **Create the Page Design + Header/Footer Partial Designs STRUCTURE, and link them** (Authoring GraphQL, minted CM-client token). **This command owns the chrome structure.** Immediately after site creation, create a **Header** Partial Design + a **Footer** Partial Design, and set the site's Page Design's `PartialDesigns` field to reference both partials (`{HEADER-PD-ID}|{FOOTER-PD-ID}`). Idempotent — skip any item that already exists.

   🔴 **READ the `Page Designs` folder BEFORE creating one, and do not assume the name.** Site templates ship their own Page Design under their own name — the `Basic` template's is **`Default`**, not `Page`. So:
   - **≥1 Page Design already present** → adopt the first one; do **not** create a second. Two Page Designs on one site are competing chrome definitions, and which one wins is a per-page field value, not a site setting.
   - **Folder empty** → create one named `Page`.

   The old wording said "create one **Page** Page Design" and the read-back below asserted that literal name, so a correctly-provisioned `Basic` site **failed a true assertion** — and the obvious "fix" (create `Page` alongside `Default`) manufactures the two-designs problem. Bind by the **id you resolved**, never by a hardcoded name. Use the GraphQL recipes in `content-sdk-website-build-flow` (Page / Partial Designs section). **Provision owns the STRUCTURE only** — it does NOT decide or place what fills the partials (that is `/author-content`'s job; rule `80` § 1: chrome = registered Header/Footer renderings inherited via the Page Design, never per-page). Record the three item IDs in `provisioning.*`.

   **HARD assert before reporting success — provision CANNOT close with empty design folders.** After the writes, read back the two Presentation folders + the link, and fail the run if the structure is absent:

   ```graphql
   {
     partials: item(where: { path: "/sitecore/content/<COLLECTION>/<SITE>/Presentation/Partial Designs", language: "en" }) {
       children { nodes { name } }
     }
     pageDesigns: item(where: { path: "/sitecore/content/<COLLECTION>/<SITE>/Presentation/Page Designs", language: "en" }) {
       children { nodes { itemId name field(name: "PartialDesigns") { value } } }
     }
   }
   ```

   **Assert ALL of:** `Partial Designs` children include both `Header` and `Footer`; `Page Designs` has **at least one** child (**any name** — `Page`, `Default`, or whatever the site template shipped); and **the Page Design you bound** carries a `PartialDesigns` value that is **non-empty and contains both partial IDs**. Assert against the **id you resolved in 7b**, not against a name — one query now returns every design with its link, so the check needs no second round trip and cannot be fooled by a same-named sibling. **Any assertion false = HARD FAILURE** — empty `Partial Designs` / `Page Designs` folders at provision close is exactly the silent skip that lets chrome land per-page instead of via the Page Design, so it is a flagged failure, **never a silent pass**: escalate per the Operator gate and do NOT report provisioning success. **`/provision-sitecoreai` ends with the Page Design + Partial Designs created and linked — asserted, not assumed.**

7c. **Ensure the COLLECTION's serialization module exists (ONE module file per collection — sites in the same collection SHARE it).** The grain is the **collection**, not the site (one module file such as `<collection-slug>.module.json` covers the whole collection). Right after the site exists:
   - **Collection already has a module** (a sibling site in the *same* collection created it) → **add this site's includes to that existing file** (a `content/<COLLECTION>/<SITE>` site include + its `Media Library/<SITE-MEDIA-ROOT>`). Do **NOT** create a second module for the same collection — that is exactly the destructive collision.
   - **New collection** → write **`cm/authoring/items/<collection-slug>/<collection-slug>.module.json`** — namespace **`Project.<COLLECTION>`**, **one FOLDER per module**, with **`items.path: "."`** and `$schema: "../../../.sitecore/schemas/ModuleFile.schema.json"`.

   🔴 **ONE FOLDER PER MODULE, `items.path: "."` — not a flat file.** Sibling `*.module.json` files in the **same directory** may not share an `includes[].name`, and they are conventional names, so collisions are the norm rather than the exception (measured on one CM: **9 of 15 include names collided across 6 modules**). The items-as-resources build then aborts with *"There are several modules … with the same include name … you should split those modules into folders"* — after MSBuild has already printed `0 Error(s)`, so it reads as a Sitecore-side failure when it is ours. A distinct `items.path` does **not** prevent this: the builder groups by **where the manifest files sit**. Because `"."` resolves the serialization root back to that same folder, **zero item YAML files move** when adopting this shape. A per-module `items.path` is still required for pull/validate isolation — without it a module defaults to the shared `items/` root and its `ser validate`/`pull` flags **other collections'** files as orphans to **DELETE** (`> Fix will delete file`). **Anything discovering manifests must scan one level deep as well as flat** — a flat `readdir` finds nothing here and reports clean.

   Scope: collection-level includes (shared by all the collection's sites) `system/Settings`, `templates`, `templates/Branches`, `Layout/Renderings`, `Layout/Placeholder Settings` (all under `Project/<COLLECTION>`) + `content/<COLLECTION>` (tenant, SingleItem); then **one site block per site** — `Media Library/<SITE-MEDIA-ROOT>` (ItemAndDescendants) + `content/<COLLECTION>/<SITE>` (**ItemAndDescendants**).

   🔴 **A module opts subtrees OUT, never in — do NOT add `{ "path": "*", "scope": "Ignored" }`.** The site include defaults to `ItemAndDescendants` and carries **no catch-all ignore**, so a subtree an author adds later is serialized without a config change. A `rules[]` entry changes a subtree's **push policy only**, not whether it is included. The retired opt-in shape (list six subtrees, ignore the rest) cost two measured classes of silent loss: `/home` pinned to `SingleItem` serialized the home item and **none of its pages**, and `/Media` + `/Settings` were under-scoped so grandchildren vanished. Every live brand had been hand-corrected, so the template stayed wrong while looking fixed everywhere it mattered.

   **Push policy by class:** dev items (`templates`, `Layout/Renderings`, `Placeholder Settings`) `CreateUpdateAndDelete`; content + media `CreateAndUpdate` (a push must **never** delete an authored page or image); environment-coupled `Site Grouping` hostnames `CreateOnly`.

   🔴 **NEVER serialize a rendering-host item.** No include may cover `/sitecore/system/Settings/Services/Rendering Hosts`. Its fields are absolute editing-host URLs for **one** tenant, and `CreateOnly` does not mitigate it — on a fresh instance it still *creates* the item with dead URLs and then refuses to correct them (a new tenant inherited a foreign org's `-eh` host exactly this way). The binding is environment state, not source: step **7d** sets the site-grouping `RenderingHost` field, which names the host by **string** and needs no serialized item. `cm/scripts/assert-module-scope.mjs` **rejects** such an include and gates modules before any push.

   This collection module is what **both** pulls operate on — the baseline pull now (step 9) and the final content pull at `/publish` — always scoped `-i "Project.<COLLECTION>"`, never anything wider.

7d. **Bind the site to its editing host — set the site-grouping `RenderingHost` field (ENFORCED).** The JSS Site Grouping item (`<COLLECTION>/<SITE>/Settings/Site Grouping/<SITE>`) carries a **`RenderingHost`** field — the Pages UI label is *"Predefined application editing host"* — that defaults to **`Default`** (the tenant-default rendering host, which serves **none of this site's renderings**). Leave it `Default` and **every component renders as "missing" in Pages** — a silent, editor-only trap: the public/live head app renders fine (its own deploy), but an author opening Pages sees an all-missing layout. Set it to the **editing-host name** — the exact string used for `renderingHosts.<key>` / `editinghost create -n <name>` (e.g. `<editing-host-name>`). Do this **right after the site + editing host both exist** (the EH's rendering host is registered into the CM host list at `editinghost create`, step 5). Raw AGQL `updateItem` (config field, rule 83, minted CM-client token), then **read back and assert** `RenderingHost` == the EH name. **The editing host that this binds to must serve THIS site's built code** — the initial EH deploy (step 5) covers the scaffold; if the go-live deploys the head app elsewhere (e.g. Vercel) instead of re-deploying the SitecoreAI EH, either re-deploy the EH with the finished code at `/publish` or point the `<eh-name>` rendering host at the live host, or Pages stays all-missing even with the binding correct.

7e. **Seed the site's `RobotsContent` — ENFORCED (read-back), CREATE-IF-EMPTY.** The site Settings item (`<COLLECTION>/<SITE>/Settings`, Pages label *Robots → Robots content*) carries a **shared** `RobotsContent` field (`{64971FA7-F8AC-4C88-9BB2-2949F2A28670}`). **An empty field does NOT mean "no robots.txt" — it means `Disallow: /`.** Sitecore composes the document server-side and Edge returns it over `site { siteInfo(site:$siteName) { robots } }`, so an unset field yields a literal `User-agent: *\nDisallow: /` and the head app's `createRobotsRouteHandler` serves it as a clean **HTTP 200**. Every crawler honours that: the site you just launched is excluded from search, silently, with nothing in `/test`, `/test-content` or the build reading `/robots.txt`. (The SDK's own `if (!robotsContent)` 404 fallback in `route-handler/robots-route-handler.js` is **dead code** — Edge never returns null, so the field is the *only* control surface.) Measured 2026-08-12 on one CM: **5 of 6 sites were shipping `Disallow: /`**; the one that wasn't had been fixed by hand.

   Right after the site exists, read `RobotsContent` and — **only when it is empty or absent** — set it to the default via raw AGQL `updateItem` (config field, rule 83, minted CM-client token):

   ```
   User-Agent: *
   Allow: /
   ```

   **Under `variables.delivery_visibility: private`** (the `method:clone` default) seed the OPPOSITE — `User-agent: *` / `Disallow: /` — and invert the read-back below: assert the field contains `Disallow: /`. A private site's robots body is its second line of defence behind the access gate (`/publish` § "Delivery visibility").

   **Never overwrite a non-empty value.** A populated field is a deliberate operator decision (a dogfood or staging site may legitimately want crawlers out), and this step is idempotent across re-runs by construction. Then **read back and assert** the field is non-empty and does not contain `Disallow: /`. **The value takes effect without a publish** — verified 2026-08-12, the preview and live Edge contexts return byte-identical `siteInfo.robots` for every site, so this is *not* subject to the rule `85` preview/live divergence and needs no publish ordering. Because step 7c's module includes `/Settings`, the value lands in `cm/` at the step-9 `ser pull` and is durable in git from provisioning onward.

   ⚠️ Known, **not** fixed here: Sitecore auto-appends a `Sitemap:` line pointing at the **CM host** (`https://xmc-….sitecorecloud.io/sitemap.xml`), not the site's public domain — present on every site measured, including correctly-configured ones. Out of scope for provisioning; record it in `operator_attention[]` if the run cares about SEO fidelity.

7f. **Additional languages — ONLY when `variables.languages.additional` is non-empty.** Skill: `sitecoreai-localization` § 2 steps 1-3. For each extra locale: read `languageItem(name)` first (`language(name)` answers for any culture and proves nothing), then Authoring `addLanguage({languageCode, regionCode, fallbackCode})` (works with the org client), enable it on the site's host, and run `language-census.mjs` once to record the baseline. **Never delete an environment language to undo**: it deletes every version in it, on every site of a shared CM. Edge language fallback is OFF by default; turning it on is an environment config patch (a CM deploy, rule 20): an operator decision, recorded, never applied here.

7g. **Search source — ONLY when `variables.search` is not `none` (operator-attention, UI-only).** Skill: `sitecoreai-search-sources`. The operator confirms *Content > Search sources* exists on this environment, creates the source of the recorded type, and installs Search Configuration Manager for the environment; record `provisioning.search.source_id`. For a push source the operator creates the API key and puts it in `.env` themselves (rule 20). No API creates a source; do not block the run on it: list it under `operator_attention[]`.

8. **(Editing host already deployed in step 5 — not deferred.)** A **re-deploy** of the EH happens at `/ship` once content is published + the LIVE `SITECORE_EDGE_CONTEXT_ID` is wired (rule 80 § 7) so live pages prerender — but the *initial* EH deploy is part of provisioning now (Content SDK 2.1.0 builds clean on an empty tenant).

9. **Initial (baseline) pull — SCOPED to the site's own module (step 7c).** `dotnet sitecore cloud login` → `environment connect --environment-id <cmEnvId> -aw` → **`ser pull -i "Project.<COLLECTION>"`**. This is the **first of two** pulls (empty/structural baseline now; the final content pull is `/publish` step 3) and it establishes the collection's isolated `cm/authoring/items/<collection-slug>/` folder. **Never run an unscoped `ser pull`, `ser validate --fix`, or `ser pull --force` on a shared `cm/`** — they treat *sibling sites'* serialized files as orphans and print `> Fix will delete file` for each; always pass `-i "Project.<COLLECTION>"`, and read any delete list before applying a fix. Record `provisioning.*` (env ids, hosts, **preview AND live context ids** — both, from the Deploy API env record `previewContextId`/`liveContextId`; the **live** one is what **Vercel must carry on all three env targets** (`production`, `preview`, `development`) as `SITECORE_EDGE_CONTEXT_ID` — Vercel is the LIVE go-live surface (`.agent/glossary.md` § "Preview-first delivery" → Surfaces), pinned + verified (`vercel env ls`) when Vercel is linked at `/ship` and re-verified at `/publish`; the editing host stays on the **preview** context as the content-phase preview surface — client ids, **secrets redacted**) plus the project identity (`deploy_project_name`, `project_slug`, `project_root`, `cm_code_base`) in the manifest.
