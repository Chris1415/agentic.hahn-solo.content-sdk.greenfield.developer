# agentic.hahn-solo.content-sdk.greenfield.developer

> **A personal example, not an official Sitecore product.** This repository illustrates how an agentic delivery flow can work and what it needs: a staged pipeline of Claude Code commands and agent identities, with Sitecore domain knowledge supplied as packs and skills. It is offered as is, it is not affiliated with or endorsed by Sitecore, and it **may not run end to end**: the status table below says what has actually been run, and what has not.

**Sitecore Content SDK head-app builds** — composition: platform:content-sdk.

## What the flow does

Agents are identities (`.agent/agents/`), commands are tasks (`.agent/commands/`), and packs hold the domain knowledge (`.agent/packs/`). Each stage reads a short brief that the active packs assemble for it, does one job, writes its artifacts to a run manifest, and hands over to the next. A few stages stop and ask you before going on (the spec, the design pick, the final result, and before anything touches a real tenant).

`/project:prime  →  /project:create-prd  →  /project:challenge-prd  →  /project:discover-sitecoreai  →  /project:architect  →  /project:design  →  /project:task-breakdown  →  /project:provision-sitecoreai  →  /project:implement  →  /project:code-review  →  /project:test  →  /project:ship  →  /project:author-content  →  /project:test-content  →  /project:publish`

1. `/project:prime` — Read-only reconnaissance of the repository; writes one planning note.
2. `/project:create-prd` — Scope questions, then a PRD, ADRs and a run manifest; chains into the spec review.
3. `/project:challenge-prd` — Cold-read gap analysis of the spec, then questions to the operator; carries the first hard stop.
4. `/project:discover-sitecoreai` — Read-only inventory of an existing SitecoreAI site, for builds that extend one.
5. `/project:architect` — Architecture blueprint and ADRs; sizes the deliverable and proposes a smaller first cut when it is large.
6. `/project:design` — One to three divergent UI variants as clickable prototypes, a fresh critic per prototype, and the design hard stop.
7. `/project:task-breakdown` — A task list with an execution contract and tests written first, split into component tranches.
8. `/project:provision-sitecoreai` — Creates the SitecoreAI project pieces: a content-management environment, an editing host, a site, and the baseline code.
9. `/project:implement` — Builds one component tranche at a time against the task list, with probe tranches first.
10. `/project:code-review` — Critical review of the change against the spec and the task list, then fixes.
11. `/project:test` — Test execution and smoke checks, then fixes; the implement, review and test loop repeats up to five times.
12. `/project:ship` — Ship report, short README and changelog, then a commit, a push and a pull request. A human reviews and merges.
13. `/project:author-content` — Writes page content in the brand voice the spec defines and lands it on preview through the Marketer MCP.
14. `/project:test-content` — An independent audit of the authored content as it renders; carries the final hard stop.
15. `/project:publish` — The one step that goes live: publishes, pulls the content back into git, redeploys on the live context, runs the delivery checks.

Everything else the flow ships is on-demand: `/project:status`, `/project:rubber-ducky`, `/project:create-frd`, `/project:create-bug`, `/project:document`, `/project:discover-components`, `/project:cleanup-project-planning`, `/project:research`, `/project:commit-message`, `/project:doctor`, `/project:probe`, `/project:resume`, `/project:start-flow`, `/project:triage`.

## What you need

- **Claude Code** (the CLI), with this folder as the working directory. The stages run as slash commands and as sub-agents; nothing here runs without it.
- **Node.js, git and `bash`** on the PATH (on Windows, Git Bash). The scripts under `.agent/scripts/` are Node; the mirrors are regenerated by `bash`.
- **A SitecoreAI organisation** and an **organisation-level automation client** (a "deploy admin" client from the Cloud Portal), only for the stages that provision or change a tenant (`/project:provision-sitecoreai` onward). The planning stages up to `/project:task-breakdown` do not need a tenant (reading an existing site with `/project:discover-sitecoreai` does).
- **The Sitecore Marketer MCP**, connected to that tenant, for `/project:author-content`. Setup: `.agent/packs/platform/content-sdk/reference/prerequisites.md`.
- **A GitHub account and the `gh` CLI**, for `/project:ship` (push and pull request), and **a Vercel account** for the head app that `/project:ship` and `/project:publish` deploy.
- **The design skills** `/project:design` loads. They are third-party, are never republished, and are not in this repo: `.agent/packs/platform/content-sdk/reference/design-skills.md` has the install pointers and what the stage does without them.

Without any of that you can:

- read `.agent/` — the commands, agent identities, rules, packs and the glossary (`.agent/glossary.md`);
- run `node .agent/scripts/validate-framework.mjs`, which checks that the flow is consistent with itself;
- render what a stage reads: `node .agent/scripts/resolve-packs.mjs --platform content-sdk --stage implement --md`;
- run `/project:prime` and `/project:create-prd`, the two stages recorded as run from an export (below). Neither needs a tenant.

## Known gaps

- **It has not been run end to end from an export.** The table says which stages were; the rest are either source-only (run in the private repository this is generated from, where the pipeline has shipped real sites) or not run at all.
- **A command name can collide with a Claude Code built-in.** `/design`, `/code-review`, `/doctor`, `/status` and `/resume` are the ones that did or can. Type the namespaced form (`/project:design`), and read every `/name` in the docs as `/project:name`.
- **The design stage loads five third-party skills this repo cannot ship.** Install pointers and the fallback are in `.agent/packs/platform/content-sdk/reference/design-skills.md`; without them the stage records what it lacked and carries on instead of stopping.
- **`/project:publish` cites two helper scripts that are not shipped** (`scripts/sitecore-publish.mjs`, `scripts/sitecore-site-thumbnail.mjs`). They are tied to the estate they were written for. The stage says what to do instead: the `sitecoreai-publishing` and `sitecoreai-sites` skills describe the same calls.
- **Two stages cite helpers from the author's own CM repository that the baseline here does not contain** (`cm/scripts/agql-token.mjs`, `cm/scripts/assert-module-scope.mjs`). Mint the token as the `sitecoreai-auth` skill describes, and check module scope by hand against the `sitecoreai-serialization` skill.
- **Platform facts are dated, and the platform moves.** Statements about SitecoreAI behaviour carry the date they were measured on. This repo does not document how long a new content-management hostname takes to resolve, the exact scopes of the organisation client, how to rotate a client, or the number of production environments an organisation may hold; check the Sitecore documentation and your plan.
- **The Marketer MCP endpoint carries no tenant.** Which tenant a write lands in is decided by the login, so the first write of a session is probed (rule `83-content-authoring-mcp-first`).
- **The pipeline ends at an open pull request.** `/project:ship` pushes and opens the PR; a human reviews and merges it.
- **The Claude Code mods of the source repository are not part of this flow.** The `.claude/settings.json` here registers none.
- **No support is offered.** This is an example, published as is. The repository is generated, so a change made here is lost on the next publish.

## About this repository

- `CLAUDE.md` — what this flow is and how to run it
- `.agent/` — the pipeline: commands, agents, rules, packs
- `.claude/` — commands, agents and the vendored skills this flow needs
- `knowledge/memory/` — durable reference notes (see below)

**Generated, never hand-edited.** This tree is produced from a private source repo, which you cannot regenerate from here, so a change made in this repo is lost on the next publish. `GENERATED` records the source commit, so staleness is checkable.

> **Windows: clone somewhere short.** The longest path inside this repo is **121 characters**,
> so with the 260-char `MAX_PATH` limit the clone directory itself must stay under roughly
> **129** characters. Past that, `git clone` writes what fits and **fails on the rest** —
> you get a partial checkout, not an error you can miss. Either clone near the drive root
> (`C:\src\...`) or enable long paths first:
> `git config --system core.longpaths true` (plus `LongPathsEnabled=1` in the registry).

## Memory is a hand-picked selection

This repo ships **15** memory notes, each picked by name and reworded to carry no
private specifics. They are a selection, **not a complete set** — do not read a gap as "no such trap
exists".

**Nothing loads these automatically.** They are files in this repo, not agent memory: Claude Code
reads memory from your own profile directory, not from a cloned tree. To actually use them, copy
`knowledge/memory/*.md` into your project's memory directory. Left where they are, they are
reference documentation you can grep — which is worth something, but it is not recall.
